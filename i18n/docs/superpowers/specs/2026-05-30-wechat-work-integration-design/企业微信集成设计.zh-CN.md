# 企业微信集成设计

## 概述

通过两个渠道将私人管家与企业微信集成：
1. **自建应用回调**——用户在企业微信中发送消息，应用通过现有的意图→智能体管道接收并回复。
2. **群机器人 Webhook 推送** — 应用可以主动将文本/markdown 消息推送到群聊。

计划推送 (APScheduler) 被推迟到单独的功能回合。

## 先决条件

### 企业微信管理面板设置（分步）

1. **创建一个自建应用**：
   - 前往[企业微信管理控制台](https://work.weixin.qq.com/wework_admin/frame#apps)
   - 点击“创建应用”（创建应用）
   - 填写应用名称、描述并上传图标
   - 创建完成后记下**AgentId** (应用AgentId)

2. **获取公司ID**：
   - 进入“我的企业”→“企业信息”
   - 复制 **CorpID**

3. **配置回调 URL**：
   - 在应用设置页面中，找到“接收消息”(接收消息)部分
   - 设置回调地址：`https://<your-domain>/api/wechat/callback`
   - 随机生成 **Token**（3-32 个字符、字母/数字）和 **EncodingAESKey**（43 个字符、字母/数字）- 保存这些
   - URL 验证最初会失败（服务器必须先运行）

4. **获取群机器人 Webhook**：
   - 在目标群聊中，点击“...”→“添加群机器人”（添加群机器人）
   - 给机器人起个名字
   - 复制 **Webhook URL**

ngrok http 8000

## 配置

`src/config.py` (`.env`) 中的新设置：

| 变量 | 是否必填 | 目的 |
|----------|----------|---------|
| `WECHAT_CORP_ID` | 是（用于回调） | 企业公司ID |
| `WECHAT_TOKEN` | 是（用于回调） | 回调 URL 验证令牌 |
| `WECHAT_ENCODING_AES_KEY` | 是（用于回调） | 用于消息加密的 AES 密钥 |
| `WECHAT_AGENT_ID` | 否 | 用于响应的应用 AgentId |
| `WECHAT_WEBHOOK_URL` | 是（用于推送） | 群机器人 Webhook URL |

默认全部为空。企业微信路由器仅在设置 `WECHAT_CORP_ID` 和 `WECHAT_TOKEN` 时注册，因此应用在本地调试模式下无需微信配置即可运行。

## 模块结构

```
src/wechat/
├── __init__.py          # Re-exports: WechatCrypto, WechatRouter, WechatWebhookClient
├── crypto.py            # AES-256-CBC encrypt/decrypt, SHA1 signature verification
├── messages.py          # XML parsing and construction
├── webhook.py           # Group bot HTTP push client
└── router.py            # FastAPI router factory: GET/POST /api/wechat/callback
```

依赖流：
```
crypto.py   ← stdlib only (hashlib, base64, struct)
messages.py ← crypto.py (for decrypt)
webhook.py  ← httpx (already in FastAPI ecosystem)
router.py   ← crypto.py, messages.py, intent_router, agent_registry
```

## 组件详情

### `crypto.py`

纯函数，无项目依赖：

```python
def verify_signature(token: str, timestamp: str, nonce: str,
                     msg_encrypt: str, msg_signature: str) -> bool
    # SHA1(sort([token, timestamp, nonce, msg])) == msg_signature

def decrypt(encoding_aes_key: str, msg_encrypt: str, corp_id: str) -> str
    # Base64 decode AES key → AES-256-CBC decrypt → strip PKCS#7 padding
    # → strip 16-byte random prefix → read 4-byte big-endian length
    # → extract plaintext → verify trailing CorpID → return plaintext

def encrypt(encoding_aes_key: str, msg: str, corp_id: str) -> str
    # 16-byte random + 4-byte len(network order) + msg + corp_id
    # → PKCS#7 pad → AES-256-CBC encrypt → Base64 encode
```

使用 AES（CBC 模式）的 `cryptography` 库 — 它具有内置的 PKCS#7 填充。

自定义例外：`SignatureError`、`DecryptError`、`CorpIDMismatch`。

### `messages.py`

用于解析消息的数据类，以及解析/构造函数：

```python
@dataclass
class EncryptedMessage:
    to_user_name: str
    agent_id: str
    encrypt: str

@dataclass
class InnerMessage:
    to_user_name: str
    from_user_name: str    # This becomes user_id in our pipeline
    create_time: int
    msg_type: str          # "text" (others ignored for now)
    content: str
    msg_id: str

def parse_encrypted_xml(body: bytes) -> EncryptedMessage
def parse_inner_xml(decrypted: str) -> InnerMessage
def build_reply_xml(to_user: str, from_user: str, content: str) -> str
def build_encrypted_reply_xml(encrypt: str, ...) -> str
```

非文字消息类型（图像、语音等）→回复“暂不支持该消息类型”（不支持的消息类型）。

### `webhook.py`

用于群机器人推送的简单 HTTP 客户端：

```python
class WechatWebhookClient:
    def __init__(self, webhook_url: str, client: httpx.AsyncClient | None = None)
    async def send_text(self, content: str) -> bool
    async def send_markdown(self, content: str) -> bool
```

将 JSON POST 到 Webhook URL。在 `errcode == 0` 上返回 `True`。

接受可选的 `httpx.AsyncClient` 用于连接重用和测试注入。

### `router.py`

创建 FastAPI 路由器的工厂函数：

```python
def create_wechat_router(
    intent_router: IntentRouter,
    agent_registry: AgentRegistry,
    corp_id: str,
    token: str,
    encoding_aes_key: str,
) -> APIRouter:
```

**GET `/api/wechat/callback`** — URL 验证：
1. `verify_signature(token, timestamp, nonce, echostr, msg_signature)` → 403 如果无效
2. `decrypt(encoding_aes_key, echostr, corp_id)` → 200 明文成功

**POST `/api/wechat/callback`** — 消息接收：
1. 从正文中解析加密的 XML
2. `decrypt()` → `parse_inner_xml()` → 提取 `from_user_name`、`content`
3. 运行现有管道：`intent_router.route(content)` → `agent_registry.get(intent)` → `agent.handle()`
4. 构建内部回复 XML → `encrypt()` → 包裹在外部加密 XML → 200 XML 响应

错误处理：
- 签名不匹配 → 403
- 解密/解析失败 → 200，“成功”明文（企业微信协议约定：失败也返回200，防止重试风暴，将错误记录在服务器端）
- 代理APIError →回复加密错误信息“LLM服务暂时不可用，请稍后重试。”给用户
- 非短信→回复“暂不支持该消息类型”

## `main.py` 接线

```python
# Conditional wechat router registration
if settings.wechat_corp_id and settings.wechat_token:
    wechat_router = create_wechat_router(
        intent_router=intent_router,
        agent_registry=agent_registry,
        ...
    )
    app.include_router(wechat_router)

# Webhook client (always created if URL is set)
if settings.wechat_webhook_url:
    webhook_client = WechatWebhookClient(settings.wechat_webhook_url)
```

调试端点保持不变。

## 回复时机

企业微信预计5秒内有回调响应。 DeepSeek LLM 调用可能需要 2-8 秒。对于 MVP：
- HTTP 响应在代理完成时被阻止（合理的 LLM 延迟是可接受的）
- 代码中的注释指出，如果延迟成为问题，可以将回复异步卸载到企业微信“客服消息”API

这是一个明确的范围权衡——在我们看到实际的延迟问题之前，不值得构建异步推送回复。

## 测试策略

- `crypto.py`：使用已知的企业微信测试向量进行单元测试（可根据企业微信的官方加密库进行验证）
- `messages.py`：使用示例 XML 夹具进行单元测试
- `webhook.py`：使用模拟 httpx 进行单元测试
- `router.py`：使用 `httpx.AsyncClient` 针对 FastAPI `TestClient` 进行集成测试
- 所有测试都使用 `DEEPSEEK_API_KEY=test` — 没有真正的 LLM 调用
- 现有代理/路由/意图测试没有变化

## 什么不在范围内

- 基于APScheduler的定时推送（单独的功能回合）
- 企业微信“客服消息”异步回复API
- 多种消息类型支持（图像、语音等）
- 企业微信OAuth登录/用户身份映射
- Ocr/媒体处理
