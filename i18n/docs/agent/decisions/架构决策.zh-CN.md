# 架构决策

## ADR-001：单进程 FastAPI MVP

MVP 是一个单进程 FastAPI 应用。它避免使用 Redis、Celery、Kafka、Docker 和 Kubernetes，直到产品需要它们。

推理：
- 当前的目标是本地化、易于理解的个人管家演示。
- 单一进程使调试和部署变得简单。
- 未来的调度可以在引入外部worker之前从APScheduler开始。

## ADR-002：SQLite 作为内存层

MVP 通过异步 SQLAlchemy 将训练记录和用户偏好存储在 SQLite 中。

推理：
- SQLite对于本地单用户或者小型私人使用来说已经足够了。
- 如果应用稍后迁移到 PostgreSQL，SQLAlchemy 可以保持模型层的可移植性。
- JSON 首选项允许新域添加命名空间，而无需立即迁移。

## ADR-003：规则优先意图路由

意图路由在调用 LLM 回退之前检查确定性规则。

推理：
- 通用命令应该便宜、稳定且可测试。
- LLM 回退处理自然语言变化，而不使每条路线都具有概率性。
- 无效的 LLM 输出必须安全降级为 `unknown`。

## ADR-004：每个域的代理边界

健身、总结、进餐和问答行为位于单独的代理程序包中，每个代理程序包均以 LangGraph `StateGraph` 的形式实现。

推理：
- 每个代理都可以拥有域提示、数据库访问、验证和响应整形。
- StateGraph 节点进一步隔离职责：提取、验证、持久化和格式化是单独的功能。
- 测试按领域集中。
- 未来的模块可以遵循相同的接口（状态+节点+图形+注册表），而无需重写调度程序。

## ADR-005：企业微信集成前调试端点

MVP 保留 `POST /api/debug/message` 作为第一个积分表面。

推理：
- 它使本地和自动化测试独立于企业微信回调签名和网络设置。
- 真正的企业微信回调支持应该先在这条路由旁边添加，而不是通过删除调试路由。

## ADR-006：通过LangChain ChatOpenAI进行DeepSeek

LLM 包装器使用 `langchain_openai.ChatOpenAI` 以及可配置的 DeepSeek 兼容基本 URL 和模型。

推理：
- 它将提供商详细信息集中在 `src/llm/client.py` 中。
- 测试可以模拟包装器而无需接触业务代理。
- 未来的提供者更改应该发生在包装器后面。
- LangChain的ChatOpenAI提供了与LangGraph生态系统集成的标准接口。

## ADR-007：用于智能体编排的 LangGraph StateGraph

每个代理都被实现为 LangGraph `StateGraph` 而不是线性类方法链。

推理：
- StateGraph 提供了一流的状态机，它本身支持多步骤工作流程、条件路由、错误恢复和检查点。
- 每个责任节点的分解使代理更容易测试、扩展和推理。
- LangGraph 的 `MemorySaver` 检查点以接近零的自定义代码提供多轮对话内存。
- LangGraph 是当前代理开发的行业标准，符合面试预期。
- 简单代理（QA、摘要）通过线性图保持简单。复杂代理（Fitness）获得子意图之间的条件路由。
- `handle()` 接口保持不变——调用者（路由、测试、调度程序）不受影响。

## ADR-008：将智能机器人回调与自建应用回调分开

智能机器人API回调（`/api/wechat/robot/callback`）作为独立的路由器实现，并与自建应用回调（`/api/wechat/callback`）进行路由。

推理：
- **不同的消息格式**：智能机器人发送带有嵌套字段的 JSON（`from.userid`、`text.content`、`chatid`、`response_url`），而自建应用发送 XML/平面 JSON（`FromUserName`、`Content`、`ChatId`）。尝试共享解析器会创建脆弱的分支逻辑。
- **不同的回复机制**：机器人使用通过`response_url` POST（JSON）的主动回复，而自建应用使用被动加密的XML回复。这些是根本不同的代码路径。
- **不同的加密receiveid**：机器人使用`""`（空字符串），自建应用使用CorpID。使用不同的 receiveid 值共享解密调用很容易出现错误。
- **独立配置**：将 `WECHAT_ROBOT_TOKEN`/`WECHAT_ROBOT_ENCODING_AES_KEY` 与 `WECHAT_CORP_ID`/`WECHAT_TOKEN`/`WECHAT_ENCODING_AES_KEY` 分开。每个都可以独立启用。
- **独立的故障域**：机器人回调中的错误不会破坏自建应用回调，反之亦然。
- **response_url msgtype 约束**：机器人的 `response_url` 仅支持 `markdown` 和 `template_card` 消息类型 -​​ 不支持 `text`。此限制仅适用于机器人路由器。

权衡：两个路由器（`src/wechat/router.py` 和 `src/wechat/robot_router.py`）具有一些结构相似性（GET URL 验证、POST 解密 + 签名检查）。 `src/wechat/crypto.py` 和 `src/wechat/messages.py` 中的共享加密和消息构建实用程序可防止较低层的代码重复，同时保持路由逻辑在分歧处的分离。
