# 架构决策

## ADR-001: 单进程 FastAPI MVP

MVP 是单进程 FastAPI 应用。在产品需要之前，避免引入 Redis、Celery、Kafka、Docker 和 Kubernetes。

理由:
- 当前目标是本地可理解、可演示的个人管家。
- 单进程保持调试和部署简单。
- 未来的调度需求可以先从 APScheduler 开始，再引入外部工作进程。

## ADR-002: SQLite 作为记忆层

MVP 通过异步 SQLAlchemy 将训练记录和用户偏好存储在 SQLite 中。

理由:
- SQLite 足够满足本地单用户或小规模私人使用。
- SQLAlchemy 保持模型层可移植性，后续可迁移到 PostgreSQL。
- JSON 偏好设置允许新领域添加命名空间而无需立即迁移。

## ADR-003: 规则优先的意图路由

意图路由在调用 LLM 回退之前先检查确定性规则。

理由:
- 常见命令应该廉价、稳定且可测试。
- LLM 回退处理自然语言变化，但不使每条路由都依赖概率。
- 无效的 LLM 输出必须安全降级为 `unknown`。

## ADR-004: 按领域划分 Agent 边界

健身、总结、饮食和问答行为分别位于独立的 agent 包中，每个使用 LangGraph `StateGraph` 实现。

理由:
- 每个 agent 可以拥有自己的领域提示词、DB 访问、验证和回复格式。
- StateGraph 节点进一步隔离职责：提取、验证、持久化和格式化是独立的函数。
- 测试按领域保持聚焦。
- 未来模块可以遵循相同的接口（state + nodes + graph + registry），无需重写调度器。

## ADR-005: 调试端点先于企业微信集成

MVP 保留 `POST /api/debug/message` 作为首个集成接口。

理由:
- 使本地和自动化测试独立于企业微信回调的签名和网络配置。
- 真正的企业微信回调支持应在此路由旁添加，而非删除调试路由。

## ADR-006: 通过 LangChain ChatOpenAI 调用 DeepSeek

LLM 包装器使用 `langchain_openai.ChatOpenAI`，可配置 DeepSeek 兼容的 base URL 和模型。

理由:
- 将提供商细节集中在 `src/llm/client.py` 中。
- 测试可以 mock 包装器而不触碰业务 agent。
- 未来的提供商更改应在包装器后进行。
- LangChain 的 ChatOpenAI 提供了与 LangGraph 生态系统集成的标准接口。

## ADR-007: LangGraph StateGraph 用于 Agent 编排

每个 agent 使用 LangGraph `StateGraph` 实现，而非线性类方法链。

理由:
- StateGraph 提供一等公民的状态机，原生支持多步工作流、条件路由、错误恢复和断点检查。
- 按职责拆分为节点使 agent 更易测试、扩展和理解。
- LangGraph 的 `MemorySaver` 断点检查以近乎零自定义代码提供多轮对话记忆。
- LangGraph 是当前 agent 开发的行业标准，符合面试预期。
- 简单 agent（QA、Summary）保持简单线性图。复杂 agent（Fitness）获得子意图间的条件路由。
- `handle()` 接口保持完全相同——调用方（路由、测试、调度器）不受影响。

## ADR-008: 智能机器人回调与自建应用回调分离

智能机器人 API 回调（`/api/wechat/robot/callback`）作为独立路由和 router 实现，与自建应用回调（`/api/wechat/callback`）分离。

理由:
- **不同的消息格式**: 智能机器人发送嵌套 JSON（`from.userid`、`text.content`、`chatid`、`response_url`），而自建应用发送 XML/平铺 JSON（`FromUserName`、`Content`、`ChatId`）。试图共享解析器会产生脆弱的分支逻辑。
- **不同的回复机制**: 机器人通过 `response_url` POST 主动回复（JSON），而自建应用使用被动加密 XML 回复。这是根本不同的代码路径。
- **不同的加密 receiveid**: 机器人使用 `""`（空字符串），自建应用使用 CorpID。以不同的 receiveid 值共享 decrypt 调用容易出错。
- **独立配置**: 将 `WECHAT_ROBOT_TOKEN`/`WECHAT_ROBOT_ENCODING_AES_KEY` 与 `WECHAT_CORP_ID`/`WECHAT_TOKEN`/`WECHAT_ENCODING_AES_KEY` 分离。每个都可以独立启用。
- **独立故障域**: 机器人回调中的 bug 不会破坏自建应用回调，反之亦然。
- **response_url msgtype 约束**: 机器人的 `response_url` 仅支持 `markdown` 和 `template_card` msgtype——不支持 `text`。此约束仅适用于机器人 router。

权衡: 两个 router（`src/wechat/router.py` 和 `src/wechat/robot_router.py`）共享一些结构相似性（GET URL 验证、POST 解密 + 签名检查）。`src/wechat/crypto.py` 和 `src/wechat/messages.py` 中的共享加解密和消息构建工具防止了底层代码重复，同时在路由逻辑分叉的地方保持分离。
